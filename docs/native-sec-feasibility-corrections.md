## What the clocks now mean

The pinned V1 schedule remains09:30–10:10NY, enrollment through09:34, and41 fixed capture slots. The last request is10seconds before the declared end; slow operations retain their actual clocks. A process launched pre-open waits for the declared readiness/launch window rather than expiring ten seconds after launch. The absolute capture deadline does not shorten a40-minute observation to9minutes. Shutdown grace permits final persistence but does not authorize new requests after the plan's existing end rules. The source watcher retains its existing job/session deadline and is never cancelled by capture failure.

The virtual clock advances over the full interval, executing producer heartbeats, all scheduled requests, response waits and upload waits. It also drives the transport's existing timeout operations; default real timers remain unchanged. Physical-process tests are complementary integration evidence, not a substitute for the full logical schedule. They remain synthetic, with zero genuine admissions.

## Source integrity is not heartbeat coverage

The new **archive-format** `NATIVE_SEC_AVAILABLE_RUN_BUNDLE_V2` is not the proposed paper-protocol V2. It stores the exact committed prefix, original final/progress snapshot and separately labelled interrupted bytes. A valid hash chain with partial heartbeat coverage remains available evidence; missing configured minutes remain uncertainty. Source failure, interrupted capture or unknown earlier history is not repaired by later observations. No original archive or frozen result is rewritten.

The same-day client returns exactly:

* `VERIFIED_NO_EARLIER_SAME_DAY_RUN`: complete scoped run/job history establishes absence; this says nothing about global history.
* `AUTHENTICATED_EARLIER_SAME_DAY_EVIDENCE`: original earlier source prefixes are available and transport-verified, even with partial heartbeat coverage. Source-capture completeness and SEC authenticity remain separate fields.
* `UNKNOWN_MISSING_OR_AMBIGUOUS_HISTORY`: missing/ambiguous/private/expired evidence, incomplete job/run history, active earlier execution, changed metadata or exceeded bounds. Any authenticated prefixes already obtained remain retained. A later event's original-ingestion field remains unknown in the read-side view; its recorded clock is preserved separately as available evidence.

Runs are bounded at40 total workflow records/two pages, at most4 potentially overlapping earlier runs, and100 jobs per run with `filter=all`. The client requires complete returned histories within those bounds; exceeding them is UNKNOWN, never a claimed absence. It also checks older potentially overlapping/active runs instead of assuming creation before midnight proves inactivity. A cancelled run is ignored only when terminal cancellation, explicit null run start and complete job history with no started jobs establish it never executed. Retry-attempt ambiguity remains UNKNOWN. Independent source pins, original ZIP/hash checks and final metadata revalidation are required. Stage descriptors retain separate bundle files without overwriting original evidence.

This proposal remains conservative: the new view returns no primary `events` until continuity/admission policy review; all retained observations and exclusions stay in `researchEvents` and original encrypted source assets. An earlier issuer observation lacking a contemporaneous class mapping cannot be replaced by a later conveniently mapped clock. None of this authorizes new collection or claims that persistent zero primary cases meets the owner's aims.

## Artifact client: implemented behavior and source correction

The stock inspected SDK defaults to up to5 Twirp attempts and120seconds of retry waiting; its Azure pipeline also has retry machinery. The implementation does not import or execute those SDKs. It uses their pinned JSON field names, scalar wrapper encoding, token-scope contract and block-blob format in a small reviewable adapter with no retry path. Per upload: CreateArtifact, one/two8MiB Put Blocks, Put Block List, FinalizeArtifact — at most5 physical HTTP calls. Redirects are manual and rejected; runtime authorization is sent only to the pinned results origin, never to signed blob storage. Explicit origin allowlists, input hashes, byte/request limits, cancellation, one in-flight upload and uncertain-failure stop state are enforced before further requests. No successful ACK is reported before a valid finalize result and immutable-file recheck.

The official reference is `@actions/artifact`6.3.1 (artifact service format7) and `@azure/storage-blob`12.31.0. That service-format number is independent of research-protocol V2.
