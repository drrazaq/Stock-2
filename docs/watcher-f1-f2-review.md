## F1: persistent bounded retries and visibility

Previously the60-second cooldown existed only in a process-local map. Restart reset it; failed final delivery-state publication had no retry path. The message record now retains attempt count, next retry time, finalization attempt count and pending-publication state. Atomic local writes are fsynced before replacement. A crash during an outcome write leaves the prior durable reservation, which suppresses replay and remains visible as unresolved.

Per logical key, the production default is at most **8 reservation attempts**, with **60,120,240,480,900,900,900-second** minimum intervals (15-minute cap). Finalization publication is separately limited to8 total attempts, one eligible finalization at most per observation cycle; the existing publisher bounds each operation to its4-second budget and at most3 internal compare/publish attempts. Counters/cooldown survive process restart when state is available. Existing caller windows and current stop conditions still apply; cooldown expiry never grants permission to send stale or ineligible content. Exhaustion requires review, not silent reset or an automatic fresh key.

Durable remote reservation remains mandatory before transport. A failed publication is unsent; it does not consume a permanent delivered key. A definite transport rejection is retryable only after its UNSENT outcome is confirmed remotely and cooldown permits. Acknowledged and uncertain outcomes remain distinct and never become resend permission. Finalization recovery publishes the saved outcome only; it sends nothing. Remote owner checks remain authoritative under competing writers. A remote cooldown or newer attempt counter rejects a stale local claim and returns the current state; malformed retry fields become UNCERTAIN. Three real-remote publisher regressions cover cooldown, stale attempts and malformed state.

Progress/final archives expose pending outcomes, waiting/exhausted retries and reserved/uncertain state. The health reader uses the newest timestamped delivery report for the day, avoiding a permanent alarm from cumulative transient failures after recovery. Any unresolved retry, exhausted budget or reserved/uncertain outcome is actionable; configured-window coverage and the known unmonitored last hour stay separate. Legacy snapshots without these fields do not manufacture delivery proof.

## F2: actual recovery contract

The actual production v4 caller could rebuild `radar-v3-snap.json` on restart despite the documentation promising a frozen retry. V5 reuses the same-day frozen snapshot when message state or prior radar research exists. It neither reruns catalyst collection for that retry nor regenerates enrollment. If the snapshot is absent/wrong-day, the radar retry is blocked and logged; saved research and message state remain intact. The snapshot is now staged in ordinary end-of-run publication and included in failure artifacts. This adds no provider calls or alternate scoring rule.

The complete-session duplicate guard still uses configured09:30–15:00 inclusive coverage, not16:00. It may perform one bounded pending-outcome publication and archives its delivery-recovery status, then exits without observation or message replay. An incomplete prior run still permits legitimate observation recovery under B1. In the observation loop, finalization recovery runs before the next cycle; it never delays indefinitely or terminates observation on publication refusal.

**Recovery limits:** the runtime does not automatically download a different run’s artifacts or replay a frozen message merely because an artifact exists. Confirmed remote state is read from the ordinary checkout. Local unpublished state and snapshot can survive restart on the same filesystem; the existing always-upload step retains local state/snapshot/research intent for7days when Actions can execute it. Hard runner loss can prevent upload; no recoverability guarantee is claimed. If the remote has RESERVED without a recoverable authenticated outcome, delivery is uncertain and suppressed. Never clear that reservation to obtain another send. If publication failed before reservation, no send occurred; local backoff may be unavailable after total host loss, but a new attempt still needs current durable remote permission. Manual restoration from an artifact is a separately reviewed operation: preserve original artifacts, verify day/source/run/provenance and current remote owner/state, restore only isolated recovery context, never overwrite remote reservation evidence or original ledgers. Missing/corrupt/conflicting recovery stays blocked; this release installs no automatic cross-run recovery or cancellation mechanism.
