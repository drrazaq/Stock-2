# Account-wide unknown-outcome quarantine

Per-operation deduplication alone is insufficient: changing the date/client_order_id could evade an older unresolved request. The guard now reserves a private account-wide CAS lock before per-operation intent and retains it for any missing/refused/unknown/unconfirmed reservation or broker/ACK outcome. A fresh operation ID, buy, sell or cancel cannot bypass it. Only a remotely durable operation ACK and remotely confirmed account-lock release allow a later distinct operation. An ACK release response loss is not reported as success. Read-only broker and research requests remain available; this does not halt the whole research system.

All journal metadata stays in the existing private-data repository as opaque hashes/status/time/UUID; no body/token/owner amount. Tests simulate all writes, races, client-ID changes, timeouts, redirects and lost responses; no real private-repository or broker operation occurs. Twelve journal contracts, six adapter and seven caller contracts cover the current three broker mutation paths. Default remains off. No order, production deployment or permission change is authorized. Manual read-only reconciliation of unknown broker state and explicit owner approval precede any future reviewed release/retry; no automatic override is added.

A confirmed operation currently entails ten bounded GitHub API requests (two initial reads, four conditional writes and their read-backs). This is a future-execution safety prerequisite, not measured live quota/latency or a production activation. Existing private-data permissions/token are not changed. Before future deployment review migration of pre-existing paper pending records and the private-journal path/limits; current engineering never touches those records.
