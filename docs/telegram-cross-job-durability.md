# Cross-job Telegram delivery journal (development only)

The shared Telegram facade now accepts an explicit durability object {store,scope,eventId}. No workflow, secret binding, permission, schedule or production behavior is changed. Existing callers remain unchanged until each logical message path is separately integrated/reviewed. This is infrastructure, not completion of all-path or authorized live-delivery acceptance.

The opt-in GitHub adapter uses existing Contents capability only, fixed Stock-2 repository/main-or-development scope, GET plus conditional PUT, refused redirects and15second timeouts. It stores only hashes, state, attempts and acknowledged IDs under data/telegram-delivery-ledger. It never writes the message body, raw chat ID or token. No real journal API write was performed during engineering. Future activation requires review/approval; do not add permissions to read-only workflows silently.

Reservation is remotely acknowledged before Telegram is contacted. Concurrent reservations use Git blob SHA compare-and-swap; rejected/unconfirmed writes block send. PENDING and UNKNOWN outcomes survive job replacement and suppress blind replay. Only a positive Telegram message ID yields ACK; an unconfirmed ACK write leaves a durable reservation, not permission to resend. Definitive400/401/403/404/429 with no delivered parts may retry at most three times across jobs. A changed message body cannot reuse an existing event key. Missing/unreadable state fails closed. No automatic cleanup or reconciliation deletes ambiguous outcomes.

This sacrifices automatic retry after an uncertain delivery to avoid duplicates; it does not claim exactly-once delivery or guaranteed delivery. An owner-reviewed reconciliation procedure is required for ambiguous records. GitHub storage failures can defer an alert. Stable event IDs must include the intended daily/session/report identity; price changes alone must not manufacture a new event. Existing local ledgers and old notifications are not automatically migrated or replayed.

Seven hosted regression cases cover independent store instances, shared-facade ACK replay, concurrent CAS, lost reservation responses, failed persistence, partial/ambiguous delivery, bounded explicit retries, content conflicts, malformed state and scope restrictions. Fixtures emulate GitHub/Telegram contracts; they are not an authorized live delivery test or actual VM-loss trial. Local execution remains unavailable.
